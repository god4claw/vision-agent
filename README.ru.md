# vision-agent (MVP / ранняя бета)

*Read this in [English](README.md).*

Автономный визуальный агент — MVP / ранняя бета. Возможности этапов 2–4 (gRPC-транспорт,
нативный ONNX OCR, маховик данных и LLM-рассуждение/планирование) уже реализованы;
см. разделы ниже. Замыкает цикл:

```
экран -> восприятие -> эпизодическая память -> решение -> действие (dry-run) -> экран
```

Собран по утверждённому DEPLOY MANIFEST. **DRY-RUN по умолчанию**: реальный ввод
мышью/клавиатурой не выполняется, пока вы явно не включите живой режим.

## Статус проекта и как продолжить

Текущая точка старта для следующей сессии:

- **Набор действий** — `move`, `click`, `drag`, `key`, `none`. Модель никогда не
  выдумывает координаты; она ссылается на обнаруженный элемент по индексу, а агент
  вычисляет его центр (см. `internal/reason/reason.go`, `ToAction`).
- **Ограждения** (`internal/executor`) — allowlist (`-allow`), запретные зоны
  (`-no-go`), аварийное отключение по ESC и ограничение частоты по минимальному
  интервалу; для `drag` проверяются обе точки.
- **Телеметрия** (`internal/agent/telemetry.go`) — каждое оценённое действие
  раскладывается по корзинам progress / regress / stall, а производные
  `progress_rate`, `regress_rate`, `stall_rate`, `efficiency` и `net` пишутся
  в лог `run segment done`.
- **Выбор области экрана** — `-display N` и `-roi x,y,w,h` задают, что захватывать;
  `CaptureOrigin` смещает координаты действий обратно в абсолютное экранное
  пространство, чтобы клик попадал точно на область / второй / виртуальный монитор.

**Известный риск (проверено на практике):** в режиме `-live` на **основном** дисплее
агент видит и может кликнуть по **собственным окнам** (терминал/IDE), что способно
убить процесс и оставить зомби, удерживающий `bin/agent.exe`. Всегда изолируйте
живые прогоны через `-display`/`-roi` на отдельный (или виртуальный) экран, держите
ESC наготове, а если прогон завершился аварийно — выполните
`taskkill /IM agent.exe /F` перед пересборкой.

**Следующие шаги:** изолировать живые прогоны на виртуальном/втором дисплее;
экспортировать телеметрию в CSV/JSON для графиков во времени; попробовать более
крупную модель-рассуждатель, чтобы улучшить наведение (снизить `stall_rate`).

## Стек

| Слой | Реализация |
|------|------------|
| Оркестрация | Go (один бинарник) |
| Захват экрана | Go, `kbinani/screenshot` (Windows win32, без CGo) |
| Восприятие (OCR) | Python-сайдкар (RapidOCR) **или** нативный ONNX в Go (`internal/ocr`, PP-OCRv6 через `onnxruntime_go`) |
| Память | `chromem-go` (встроенное векторное хранилище) |
| Эмбеддинги | Локальный офлайн-эмбеддер по умолчанию; Ollama опционально |
| Действия | Dry-run исполнитель по умолчанию; реальный ввод + ограждения через `-live` |
| IPC | HTTP/JSON, gRPC или внутрипроцессный нативный (`-transport`) |

## Требования

- Go 1.25+
- Python 3.10+ (только для HTTP/gRPC-сайдкара восприятия)
- Компилятор C (Mingw-w64 gcc) + `CGO_ENABLED=1` — только для `-transport native`
- Ollama (опционально, только если используете `-embed-model`)

## Запуск

1. Запустите сайдкар восприятия (в отдельном терминале):

```powershell
python perception/server.py
```

2. Запустите агента (dry-run, 200 итераций):

```powershell
go run ./cmd/agent -iters 200
```

Бесконечный цикл (остановка по Ctrl+C):

```powershell
go run ./cmd/agent
```

### Полезные флаги

```
-iters N           максимум итераций (0 = бесконечно)
-tick MS           задержка между итерациями (по умолчанию 200ms)
-transport T       транспорт восприятия: http | grpc (по умолчанию http)
-perception URL    URL сайдкара (транспорт http, по умолчанию http://127.0.0.1:8089)
-grpc-addr ADDR    gRPC-адрес восприятия (транспорт grpc, по умолчанию 127.0.0.1:8090)
-embed-model NAME  использовать эмбеддинги Ollama (например nomic-embed-text); пусто = локальные
-max-episodes N    ограничение объёма памяти (по умолчанию 5000)
-roi "x,y,w,h"     OCR только этой области экрана (по умолчанию: весь дисплей)
-diff F            порог разницы кадров; пропускать OCR, если изменение кадра <= F (0 = всегда OCR; по умолчанию 1.5)
-live              ВКЛЮЧИТЬ РЕАЛЬНЫЕ ДЕЙСТВИЯ (по умолчанию выключено)
-memory-dir DIR    сохранять эпизодическую память между запусками (пусто = в памяти, очищается при выходе)
-telemetry-out F   записать финальный снимок телеметрии в F при выходе (.csv или .json)
-metrics-addr ADDR отдавать Prometheus /metrics на ADDR (например 127.0.0.1:9090; пусто = выключено)
-version           вывести версию и выйти
```

## Запуск через gRPC

1. Запустите gRPC-сайдкар (использует тот же OCR-движок):

```powershell
python perception/grpc_server.py
```

2. Направьте агента на него:

```powershell
go run ./cmd/agent -transport grpc -iters 200
```

Протокол описан в `proto/perception.proto`. Чтобы перегенерировать стабы после
правки proto (Go-плагины должны быть в PATH через `go install`):

```powershell
$env:Path = "$(go env GOPATH)\bin;" + $env:Path
python -m grpc_tools.protoc -I proto --go_out=. --go_opt=module=visionagent --go-grpc_out=. --go-grpc_opt=module=visionagent --python_out=perception --grpc_python_out=perception proto/perception.proto
```

## Полностью нативный запуск (этап 4, без Python)

Транспорт `native` выполняет ONNX-модели детекции и распознавания PP-OCRv6
внутри процесса через `onnxruntime_go` (CGo). Python-сайдкар не нужен.

Вендоренные ассеты лежат в `assets/`:

```
assets/onnxruntime.dll              разделяемая библиотека onnxruntime
assets/onnxruntime_providers_shared.dll
assets/models/{det,rec,cls}.onnx    PP-OCRv6 детекция / распознавание / угол
assets/ppocr_keys.txt               словарь символов распознавания (классы CTC)
```

Сборка и запуск (CGo требует gcc в PATH):

```powershell
$env:CGO_ENABLED = 1
$env:Path = "C:\ProgramData\mingw64\mingw64\bin;" + $env:Path
go run ./cmd/agent -transport native -iters 200
```

Нативные флаги: `-native-recognize=false` (только рамки детекции), `-det-model`,
`-rec-model`, `-rec-keys`, `-ort-dll`, а также флаги маховика `-collect`,
`-collect-thresh`, `-collect-dir`, `-watch-models`.

Детекция выдаёт повёрнутые прямоугольники минимальной площади (выпуклая оболочка +
вращающиеся штангенциркули), а распознавание выполняется дополненными батчами
ради пропускной способности.

Посмотреть, что движок видит на вашем экране:

```powershell
go run ./cmd/ocrprobe -top 25
```

Перегенерировать словарь символов из метаданных rec-модели:

```powershell
python scripts/extract_dict.py
```

## Маховик данных (этап 3)

Нативный движок может логировать собственные распознавания с низкой уверенностью
для последующего дообучения и подхватывать переобученную модель «на лету», без
перезапуска:

```powershell
# собирать сложные примеры во время работы
go run ./cmd/agent -transport native -collect -collect-thresh 0.85 -iters 500

# подхватить переобученную модель вживую
go run ./cmd/agent -transport native -watch-models -diff 0
```

Полный цикл (сбор -> корректировка -> дообучение -> экспорт -> горячая замена)
описан в `docs/FLYWHEEL.md`.

## Производительность: кэш по разнице кадров

Агент пропускает дорогой вызов OCR, когда кадр практически не изменился
(сигнатура 16x16 в оттенках серого сравнивается с `-diff`). На статичном экране
это резко снижает среднюю задержку восприятия (замерено ~3200 мс -> ~370 мс на
10 итерациях: 1 реальный OCR + 9 попаданий в кэш). Комбинируйте с `-roi`, чтобы
ещё сильнее сократить площадь OCR. Лог прогона сообщает `avg_perceive`,
`cache_hits`, `cache_misses`.

## Производительность: внимание (diff-ROI)

`-attn` — более тонкая, не зависящая от транспорта стратегия пропуска, которая
переопределяет полнокадровый кэш. Она разбивает кадр на плитки (`-attn-tile`,
по умолчанию 32 px), определяет, какие плитки изменились с прошлого кадра
(`-attn-thresh`), и запускает OCR только на охватывающей области изменившихся
плиток, объединяя свежие рамки с закэшированными рамками неизменившейся части
экрана:

```powershell
go run ./cmd/agent -transport native -attn -iters 200
```

Лог прогона сообщает `attn_full` / `attn_partial` / `attn_skipped`. Обратите
внимание: «грязная» область — это один общий охватывающий прямоугольник всех
изменившихся плиток, поэтому разбросанные изменения (например мигающий курсор
плюс часы в противоположных углах) могут его расширить; наибольший выигрыш дают
сгруппированные изменения.

## Политика решений: LLM-рассуждатель

По умолчанию агент использует крошечную встроенную эвристику (воспроизвести
ближайшее воспоминание, иначе кликнуть по первому элементу). С флагом `-reasoner`
он вместо этого просит локальную модель Ollama выбирать каждое действие в
направлении цели `-goal`:

```powershell
go run ./cmd/agent -transport native -ep directml -ep-device 1 \
    -ort-dll assets/dml/onnxruntime.dll -attn \
    -reasoner -reason-model llama3.2:1b -goal "open the File menu"
```

Модель никогда не выдумывает координаты в пикселях: обнаруженные перцептором
текстовые рамки подаются как нумерованный список, а модель отвечает строгим JSON
(`format:"json"`), называя действие и индекс элемента. Поддерживаются действия
`click`, `move` (навести курсор на элемент без клика; `hover` — синоним),
`drag` (нажать на элементе `target`, перетащить к элементу `to`, отпустить),
`key` и `none`:

```json
{"action":"click","target":0,"key":"","reason":"open the file menu"}
{"action":"move","target":2,"key":"","reason":"hover over the File menu"}
{"action":"drag","target":3,"to":7,"key":"","reason":"drag file into folder"}
```

Агент преобразует индекс обратно в центр элемента (`reason.ToAction`). Действия
с клавишами проверяются по белому списку (`executor.ValidKey`): принимаются
только реально нажимаемые клавиши/сочетания (`a`, `Enter`, `Ctrl+Shift+P`, `F5`, ...),
поэтому LLM, «нажимающая» предложение вроде `"Editor"`, отклоняется до любого
ввода. Любой сбой рассуждателя (недоступная модель, битый JSON, индекс вне
диапазона, недопустимая клавиша) **мягко деградирует** до эвристики и не
считается ошибкой цикла, так что нестабильная модель никогда не застопорит цикл.
Качество решений растёт вместе с моделью: крошечные модели (например
`llama3.2:1b`) часто выдают валидный JSON, но слабые решения; для осмысленных
действий загрузите модель побольше (`ollama pull llama3.2:3b` / `qwen2.5:7b`).

## Многошаговое планирование

`-plan` (вместе с `-goal`) раскладывает высокоуровневую цель на упорядоченный
список конкретных подшагов через планировщик Ollama (`reason.OllamaPlanner.Plan`)
и затем выполняет их по одному:

```powershell
go run ./cmd/agent -transport native -ep directml -ep-device 1 \
    -ort-dll assets/dml/onnxruntime.dll -attn \
    -reasoner -reason-model llama3.2:3b -plan \
    -goal "open the File menu and click New File"
```

На каждом такте агент передаёт рассуждателю **текущий подшаг** (а не всю цель).
Перед выбором он спрашивает у планировщика `StepComplete(step, screen)` и
продвигает курсор мимо всех ведущих подшагов, которым экран уже удовлетворяет
(так пропускаются уже выполненные префиксы). Награда тоже начисляется
относительно активного подшага. Сбой планирования оставляет план пустым, и агент
идёт к цели напрямую. План хранится в `agent.Plan` (шаги + курсор); когда он
исчерпан, `Current()` откатывается к общей цели.

Замечание о стоимости: планирование добавляет один вызов на старте и по одному
вызову `StepComplete` на такт поверх вызова принятия решения — это самый тяжёлый
из LLM-режимов, поэтому он включается явно.

## Обучение: награда и эпизодическая память

Агент обучается без какого-либо обучения моделей. Каждое действие оценивается
**заземлённым сигналом награды**: действие «удалось», если после него изменился
экран (значит, оно что-то сделало); no-op не засчитывается никогда
(`scoreSuccess`). Поскольку эффект действия виден только на *следующем* кадре,
оценка **отложена на один такт** — агент удерживает ожидающее действие и
разрешает его эпизод по следующему наблюдению, после чего сохраняет его с
настоящим флагом успеха (никаких больше зашитых `Success: true`).

Воспроизведение ограничено похожестью: эвристика повторяет запомненное действие
только если прошлый эпизод был успешным **и** косинусная близость текущего
состояния к нему `>= -replay-threshold` (по умолчанию `0.7`), поэтому
несвязанный экран никогда не вызовет устаревший повтор. LLM-рассуждателю тоже
подаются только *успешные* близкие эпизоды в качестве ориентира. Память
ограничена значением `-max-episodes` (самые старые вытесняются).

### Награда с учётом цели

Базовый сигнал «экран изменился» знает лишь, что действие *что-то сделало*, но не
то, *помогло* ли оно. С флагом `-goal-reward` (и заданной `-goal`) награда вместо
этого приходит от **судьи** Ollama (`reason.OllamaScorer`): ему показывают цель
плюс текст экрана до и после действия, а он возвращает `{"progress": true|false}`.
Так действие засчитывается только тогда, когда экран стал *ближе к цели*:

```powershell
go run ./cmd/agent -transport native -ep directml -ep-device 1 \
    -ort-dll assets/dml/onnxruntime.dll -attn \
    -reasoner -reason-model llama3.2:3b \
    -goal "open the File menu" -goal-reward
```

Это добавляет второй вызов LLM на каждый оценённый такт. Сбой судьи мягко
деградирует до базового сигнала «экран изменился» и никогда не считается ошибкой
цикла. No-op действия не оцениваются никогда.

Вердикты мемоизируются ограниченным `CachingScorer` (`-score-cache`, по умолчанию
4096): идентичный переход `(goal, before, after)` судится только один раз,
поэтому статичные или повторяющиеся экраны не стоят дополнительных вызовов LLM.
Лог прогона сообщает `score_hits` / `score_misses` (например, статичный экран
даёт ~80% попаданий). Ошибки не кэшируются.

## Ускорение на GPU (DirectML)

`-ep directml` выполняет инференс на любом Windows-GPU через провайдер исполнения
DirectML; `-ep cuda` нацелен на NVIDIA + CUDA/cuDNN. Для этого нужен
`onnxruntime.dll` со включённым DirectML (CPU-сборка его не поддерживает), версия
C-API ORT которого совпадает с биндингом `onnxruntime_go` (сейчас API 26 -> ORT 1.27).
DirectML-сборка `onnxruntime.dll` (1.27, канал ORT-Nightly) плюс `DirectML.dll`
(1.15.4) лежат в `assets/dml/`:

```powershell
go run ./cmd/agent -transport native -ep directml -ep-device 1 \
    -ort-dll assets/dml/onnxruntime.dll
```

**Выберите правильный адаптер.** Устройство DirectML 0 часто оказывается слабым
встроенным GPU. На этом ноутбуке `-ep-device 0` выбирал AMD iGPU (без ускорения),
тогда как `-ep-device 1` выбирал NVIDIA RTX 3050 Ti (подтверждено через
`nvidia-smi`: ~40% загрузки, ~840 МБ). Переберите индексы для своей машины.

**Результаты профилирования** (`-profile` логирует тайминги по стадиям).
Контролируемое A/B на одном и том же полном экране 1080p (~205 текстовых рамок):

| Стадия | CPU | DirectML (RTX) |
|--------|-----|----------------|
| detect | ~100 мс | ~30 мс (3x) |
| recognize | ~3900 мс (~18.5 мс/рамка) | ~2480 мс (~12 мс/рамка, 1.5x) |
| frame | ~4000 мс (~0.24 fps) | ~2480 мс (~0.40 fps) |

Детекция (постоянная форма входа) хорошо ускоряется на GPU. Распознавание
изначально *не было быстрее* на GPU, потому что оно батчится с динамической
шириной в каждом батче, из-за чего DirectML переоптимизировал граф на каждый
вызов. Исправление (`engine_rec.go`): на GPU-провайдерах вход rec-модели
привязывается к фиксированным **корзинам ширины** (`recBuckets`) и фиксированному
размеру батча, так что форма принимает лишь несколько значений и граф
компилируется один раз на форму. Это даёт ~1.5x на распознавании (на CPU
сохраняются плотные ширины по батчу, чтобы не тратиться на лишнее дополнение).

**Самый сильный рычаг скорости — по-прежнему сокращение числа распознаваемых
рамок на кадр:** сочетание `-ep directml -ep-device 1 -attn` снижает кадр на
статичном экране до ~150 мс (boxes=2-3) против ~2700 мс на полном CPU — примерно
в 17 раз. Полностью динамичный, насыщенный текстом экран ограничен распознаванием
на уровне ~0.4 fps (~24 кадра/мин).

## Телеметрия: progress / regress / stall

Каждое оценённое (не no-op) действие раскладывается по корзинам в
`agent.Telemetry`, чтобы можно было отслеживать, насколько эффективно агент
продвигается к цели:

- **progress** — награда решила, что действие приблизило к цели.
- **regress** — прогресса нет, но экран изменился (что-то сделано, но не помогло,
  то есть движение не в ту сторону).
- **stall** — прогресса нет и экран не изменился (нет видимого эффекта).

Лог сегмента прогона сообщает счётчики плюс производные показатели, `efficiency`
и `net` (= progress - regress), например: `scored=5 progress=2 regress=1 stall=2
progress_rate=0.40 regress_rate=0.20 efficiency=0.67 net=1`. Во время длинных
прогонов каждые 50 итераций также пишется компактная строка `telemetry`. На
статичном экране в dry-run каждое действие — это `stall` (без реального ввода
ничего не меняется), и это ожидаемая базовая линия.

Как читать метрики (какое направление здоровое):

- **`efficiency` -> чем выше, тем лучше** (главная метрика качества): доля
  полезных действий среди тех, что реально изменили экран. `efficiency=1.0`
  означает, что каждое результативное действие двигало к цели. Метрика
  игнорирует stall-ы, поэтому не размывается безобидными тактами без эффекта.
- **`progress_rate` -> чем выше, тем лучше**, **`net` -> положительный и растущий — хорошо**.
- **`regress_rate` -> чем ниже, тем лучше** (мало действий «не в ту сторону»).
- **`stall_rate` -> чем ниже, тем лучше** (мало действий без эффекта: лучше
  наведение / чаще попадание по интерактивным элементам).

Итого, здоровый агент выглядит так: *высокий `efficiency` + положительный `net` +
низкий `regress_rate` + низкий `stall_rate`*.

## Живой режим и ограждения

По умолчанию агент работает в **dry-run**: он логирует намеченные действия, но не
выполняет реального ввода. `-live` включает настоящий ввод мышью/клавиатурой
(Windows `user32.dll`: `SetCursorPos` + `mouse_event` + `keybd_event`). Реальный
ввод всегда обёрнут в `SafeExecutor`, который применяет ограждения до того, как
что-либо дойдёт до ОС:

```powershell
go run ./cmd/agent -transport native -ep directml -ep-device 1 \
    -ort-dll assets/dml/onnxruntime.dll -attn \
    -reasoner -reason-model llama3.2:3b -goal "open the File menu" \
    -live -safe-min-ms 300 -no-go "0,0,1920,40;0,1040,1920,40"
```

Ограждения:

- **Аварийное отключение** — удерживайте **ESC**, и все действия подавляются
  (`AbortRequested` опрашивает `GetAsyncKeyState`). Отпустите, чтобы продолжить.
- **Запретные зоны** (`-no-go "x,y,w,h;..."`) — клики/перемещения внутри любой
  зоны блокируются (например, оградите панель задач и заголовок окна).
- **Allowlist действий** (`-allow "move"` или `-allow "move,click"`) — когда
  задан, дальше проходят только эти типы действий; всё остальное подавляется.
  Используйте `-allow move` для прогона «только курсор», без кликов и нажатий.
- **Ограничение частоты** (`-safe-min-ms`, по умолчанию 250) — минимальная задержка
  между реальными действиями.
- **Белый список клавиш** — нажимаются только сочетания из `executor.ValidKey`.

Подавленные действия подсчитываются (`actions_done` / `actions_blocked` в логе
прогона), никогда не передаются дальше и никогда не считаются ошибками цикла.
Вне Windows реальный ввод возвращает ошибку (её ловит watchdog).
